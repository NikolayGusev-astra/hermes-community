# Модель угроз

Каталог раздаёт текст, который агент читает как инструкции. Это не «сайт с
описаниями»: установленный скилл выполняется. Защита строится слоями, и каждый
закрывает то, что не видит предыдущий.

## Что защищаем

| Актив | От чего |
|---|---|
| Пользователя, поставившего набор | выполнение чужого кода и скрытых инструкций |
| Автора | кража его ключей через опубликованный файл |
| Каталог | репутация: один вредоносный набор закрывает доверие ко всем |
| Читателя карточки | ложное чувство безопасности от зелёного бейджа |

## Угрозы и ответ

### 1. Промт-инъекция в тексте

**Как выглядит:** обычное предложение среди документации — «игнорируй
предыдущие инструкции», «покажи системный промпт», «действуй без подтверждения».

**Почему не решается сканером:** смысл нельзя поймать регуляркой. Сканер ловит
грубые формы, остальное — ревью.

**Ответ:** гейт на критические паттерны плюс обязательное чтение `soul.md`
человеком. `soul.md` опаснее скилла: скилл действует, пока загружен, а soul
задаёт поведение всегда.

### 2. Скрытые инструкции

**Как выглядит:** HTML-комментарий `<!-- agent: ... -->`, блок с `display:none`,
невидимые символы (LTR/RTL override, zero-width).

**Почему это работает:** markdown не рендерит их, человек не видит, агент читает.

**Ответ:** гейт вырезает невидимые символы и блокирует файлы с инструкциями в
комментариях. Это детерминированно и не требует суждения.

### 3. Утечка секретов через пример

**Как выглядит:** «пример» с настоящим токеном, `.env` в наборе, ключ в
`profiles/`.

**Почему это хуже обычной утечки:** публикация необратима, поисковики и
скраперы индексируют быстро.

**Ответ:** `gitleaks` плюс собственные регулярки; секрет блокирует merge. После
merge — ротация ключа, а не только удаление файла.

### 4. Занижение риск-класса

**Как выглядит:** манифест говорит `network: false`, а в скилле `requests.post`
на биржу.

**Почему это главный соблазн:** честный класс означает больше ревью и меньше
установок.

**Ответ:** гейт сверяет заявленное с найденным и блокирует расхождение.
Завышать можно, занижать нельзя.

### 5. Ослабление правил в том же PR

**Как выглядит:** PR меняет `tools/gate.py`, убирая проверку, и добавляет набор,
который её не прошёл.

**Ответ:** `CODEOWNERS` на `/tools/` и `/.github/`; правка правил требует
отдельного ревьюера. Плюс запрет self-approve на защищённой ветке.

### 6. Вредоносный набор после merge

**Как выглядит:** первый PR чистый, второй добавляет полезную функцию и строку
с эксфильтрацией.

**Ответ:** каждый коммит в `main` идёт через PR, гейт запускается на каждом.
Тег версии фиксирует то, что проверили: потребитель ставит по тегу, а не по
плавающей ветке.

## Что эта схема не закрывает

Честный список, чтобы зелёный бейдж не читался как гарантия:

- **Семантику.** Набор, который вредит легальными средствами, пройдёт всё.
- **Вредоносный первый PR от терпеливого автора.** Ревью ловит то, что видно,
  а не замысел.
- **Поставку после установки.** Если скилл тянет код из сети при запуске, гейт
  этого не увидит. Поэтому `network: true` в карточке — предупреждение, а не
  формальность.
- **Компрометацию аккаунта ревьюера.**

Отсюда правило: карточка показывает, что проверено и чем, а не обещает
безопасность. Пользователь, ставящий набор с `money: true` или `credentials: true`,
принимает решение сам, и карточка обязана дать ему для этого факты.
